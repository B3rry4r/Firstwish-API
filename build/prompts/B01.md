Cases (input -> expected), beyond P5-COMMON's per-endpoint tests:
 1. Ask for a code with " ADA@Example.com": one email goes out through the email port (stand-in captures it), the code is stored
    hashed with an expiry; the answer is the same whether or not the email has an account (no way to test for an account).
 2. Verify the code: the account exists once (ada@example.com), an access token (15 min) comes back in the body and a rotating
    refresh token (30 days) in an httpOnly, Secure, SameSite cookie scoped to the refresh route. A wrong code counts a try; after the
    tries in the declaration the code is dead; an expired or used code refuses; the same code never works twice, also when sent twice at once.
 3. Refresh rotates: the old refresh token is dead after use; using a dead one ends that whole session family (theft). Sign out ends
    one session; sign out everywhere ends all. The clock port moves time in the tests.
 4. Limits from the declaration (PROVISIONAL figures in decisions.json): resend wait, codes per email per hour, per IP per hour: each
    answers 429 with the envelope and a retry time.
 5. Google: an ID token is verified against the port (stand-in: a signed test token; real: Google's keys, audience = env client id);
    an unverified email, wrong audience or expired token refuses; a Google sign-in with an email that already has an account signs
    into THAT account (one account per email) and records the ExternalIdentity.
 6. /v1/me returns the account with sides and mode; PATCH changes name, mode (light|dark|system) and nothing a user may not change
    (422 for unknown fields); a phone given here is stored as a plain detail, never verified, never a key (R11).
